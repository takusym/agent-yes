# Adversarial review of the multi-host room proposal

Reviewed against the current checkout and installed codehost source, 2026-09-10. Static review plus two local validation probes; no live fleet benchmark or signaling attack was performed. Line references below are repository-relative; codehost references refer to the installed dependency.

**Recommendation: reject C as justified here. First exercise and finish A's existing integration. The proposal overlooks substantial working code in agent-yes itself. A still needs a security/connectivity assessment; it is not equivalent to the existing encrypted share transport.**

1. **Blocker: “`_host` is never populated” is false, and alternative A's console costs are false.** `lab/ui/index.html:2780` implements `chPeerTx`, routing every request to an explicit codehost peer. `:2887` implements `CodehostRoom`; `:2897` joins the room; `:2946` creates a source keyed by room/peerId; `:2966` sets its device label. `:5732` stamps agents, including `_src`, `_room`, `_key = source#pid`, and `_host` at `:5742`. The ordinary share transport actually fetches `/api/whoami` at `:8219` and sets `deviceLabel` at `:8220`. This is not merely a grouping helper waiting for data. The comment at `:2759` even documents an earlier multi-host routing bug and its resolution. A already feeds the agent-yes console, so “two consoles” and “room layer stays dead” are not necessary costs. Searching this HTML without `rg -a` stops at an embedded NUL, which can conceal the later implementation.

2. **Section 2 is conditionally right, but attributes the fix to the wrong thing.** Today's failure is several hosts multiplexed into one browser PeerConnection, not classic simultaneous-offer glare between the two ends of one connection. The DO gives every star host the same `"host"` identity (`lab/ui/cf/worker.ts:299`), broadcasts a browser's messages to all hosts (`:334`), and broadcasts joins (`:317`, `:365`). The browser has one `pc`, processes every offer against it, and sends untargeted answers/candidates (`lab/ui/rtc.js:168`, `:216`, `:226`, `:256`). It does not explicitly choose and discard all but one offer, as the proposal suggests.

   Unique endpoint identities, one PC per browser/host pair, and explicit bidirectional routing fix the cross-host collision. Browser-as-sole-offerer then avoids bilateral offer glare for each pair. Switching only the offerer while retaining `toHost` would just make N hosts answer one offer. With the proposed mesh-style routing, it does fix that collision: `worker.ts:327` stamps `from` and routes `to`. Host-as-offerer could also work with the same addressing. Existing `ay ch` already elects one offerer per pair (`ts/channels/peer.ts:194`, `:203`).

   Missing requirements: single-flight dialing per pair, a connection generation/attempt ID, serialized SDP transitions, queued early ICE, stale callback rejection, and collision-safe peer IDs. A roster update and a retry can otherwise both offer to the same host, or delayed ICE from an old attempt can reach a replacement connection. Codehost deduplicates browser dials (`src/web/room-client.ts:84`) but its daemon replaces a connection on every offer (`src/cli/rtc-daemon.ts:128`); these are actual mechanisms, not guarantees conferred by the offerer role. The libdatachannel storm problem remains when multiple tabs dial one host: `ts/share.ts:47` explicitly describes concurrent DTLS handshakes, and `:427` already staggers setup. Reversing who offers does not remove native handshake concurrency.

3. **Sections 1 and 5 do not safely support weak chosen tokens.** I ran the installed validator: `validateToken("Password123!")` returns `{ok:true}`. The rules are composition checks and a tiny denylist, not entropy verification (`node_modules/codehost/src/shared/token.ts:22`, `:42`). HKDF does not turn a guessable password into an unguessable secret; RFC 5869 section 4 explicitly excludes password stretching: https://www.rfc-editor.org/rfc/rfc5869.html#section-4.

   Attack: enumerate plausible passwords, compute their deterministic room IDs and auth values, and try those rooms. A known room ID also becomes an offline guess verifier, and a signaling operator sees room IDs/auth values for offline testing. A successful token guess yields the E2E key material too, so “the server never sees the token” does not preserve today's threat model. First-use TOFU makes preemptive denial easier: for a predicted room ID, register a host with an arbitrary auth token, or pin the wrong protocol/mode. `worker.ts:273` accepts the first host's chosen values; `:291` persists them and `:295` rejects later mismatches. There is no ownership proof relating the proposed derived room ID to the stored auth value. Even knowing only an unused room ID would suffice to squat it under this admission scheme; guessing the token additionally gives full control if the attacker chooses to join legitimately. Do not probe by opening a new room, since that mutates TOFU state.

   The proposal also contradicts itself: if the Worker sees only derived values, it cannot check the original password's length, character classes, or denylist membership. Codehost can enforce its rule because it receives the actual token in `/room/<token>` (`src/shared/signaling-client.ts:145`; `worker/index.ts:39`). That is a different security model.

   Prefer a high-entropy secret generated once on the provisioning/controller machine and distributed as the one cloud-init string. Randomness does not require first-boot generation. If human passwords are a product requirement, specify a separate password-authentication design; adding a slower KDF alone neither eliminates guesses nor fixes room ownership/squatting. Specify normalization, derivation domains, output encoding and protocol version as well.

4. **Section 5's “E2E unchanged” is false at integration level.** Existing `deriveAuthToken` and `deriveDirKeys` require exactly 64 lowercase hex characters, converted into 32 raw bytes (`lab/ui/e2e.js:83`, `:96`, `:111`). I verified that passing `Password123!` to the current derivation throws `invalid share token`. A token-to-secret derivation is missing. Also, transcript hashing is offer/answer ordered (`e2e.js:139`): host code currently supplies local then remote (`ts/share.ts:565`), and browser code remote then local (`lab/ui/rtc.js:262`). Both call sites must change when their SDP roles reverse; encryption directions remain host/client. Preserve mutual key confirmation. Roster `meta` sent through the DO is plaintext, outside this E2E envelope; do not claim all content stays ciphertext. Unauthenticated metadata must not become trusted host identity.

5. **Section 4 is feasible for a bounded fleet, not a fleet-scale design.** One established channel per host with multiplexed requests is reasonable. One new connection per request is not. N hosts and B tabs imply approximately N×B PCs, ICE/DTLS setups, channels, streams, and potentially TURN allocations. A single tab concentrates N connections and all list parsing, encryption, sorting, and rendering. Many tabs concentrate B native handshakes on each daemon. Actual first failure depends on device, network and fleet size; claiming an exact browser ceiling without measurement would be fiction.

   The DO is another bottleneck: current targeted relay scans every socket (`worker.ts:372`). N host signals therefore imply quadratic lookup work as N grows. Broadcasting a full N-entry roster to N members on each join/change (`codehost/worker/room.ts:232`) is quadratic bytes per broadcast; N independently changing metadata sources can produce cubic aggregate growth in a naive implementation. Limit metadata, coalesce changes, use deltas, and publish rosters only to viewers when possible. Claims that no host learns about others contradict the “DO → all” roster.

   Reuse the existing source abstraction and delta subscription (`index.html:5795`), with bounded dial concurrency, jittered retries, per-host deadlines and cancellation, incremental rendering, and explicit offline/stale status. Current fallback polling already uses `Promise.all` and renders after all requests settle (`:6245`); catching errors in `listSource` prevents rejection of the whole list (`:5769`), but a slow peer still delays that render. Requests time out at 12 seconds (`rtc.js:441`), separately from the 8-second connect deadline (`:280`). Section 3's “N × 8s” is not wall-clock latency for parallel dials; it is roughly one deadline with N stalled attempts, or several deadline waves under bounded concurrency. Do not silently drop machines from the UI and call that correct degradation. An empty newly provisioned host must remain visible and be selectable for spawn.

6. **Identity is not a label, and “cosmetic” impersonation is wrong.** `layeredRows` groups by `_host` and then builds PID parent forests (`console-logic.js:622`, `:626`; `:460`). Equal user/hostname labels can merge two machines' trees and falsely attach their agents. A label suffix alone is a fragile identity scheme. Group and route by a non-label source ID; display a separate label. Keep room/signaling context in keys as the console already does (`index.html:5742`), not bare `peerId:pid` globally. Specify stable machine ID versus connection/session ID, duplicate registration handling, image cloning, daemon restart, and PID reuse. Codehost explicitly distinguishes persisted `hostId` from per-process `peerId` (`shared/signaling.ts:79`). Its DO currently accepts client-supplied peer IDs without a uniqueness check and routes to the first match (`worker/room.ts:78`, `:216`), so blindly copying it imports impersonation/routing ambiguity.

   Every host containing the common token can act as a browser against every other host. Hiding rosters or calling a socket “host” cannot enforce a lesser capability. Compromising one fleet member compromises this shared capability across the fleet. If enrollment-only hosts or individual revocation are required, a single common bearer token cannot supply them. Misleading an operator into sending a command to an attacker-controlled machine is a security issue, not cosmetic.

7. **Liveness and compatibility need explicit designs.** Current agent-yes pings are edge-auto-answered without waking the DO (`worker.ts:230`, `:321`). Copying a handler that updates `lastSeen` will not observe those exact pings; naive timeout eviction would evict healthy members. Codehost's implementation touches ping state (`worker/room.ts:94`) but backs its sweep off until it stops entirely (`:25`, `:144`), so its protocol comment does not prove bounded stale-member eviction. Agent-yes already has a four-minute signaling recycle because edge pong is insufficient proof of working signaling (`ts/share.ts:31`). Define browser suspension behavior, stale routing health, removal semantics for still-working data channels, and the cost of the chosen liveness SLA.

   Mode TOFU is boolean today and unknown hello fields are ignored (`worker.ts:283`). A new fleet client talking to an old Worker can silently be treated as star unless the client demands explicit version/mode acknowledgement. Use an explicit versioned fleet namespace/protocol and reject unsupported modes before dialing. Define upgrades of pinned rooms. Existing share rejection handling can mint a new random room (`ts/share.ts:376`, `:590`): never inherit this behavior for a deterministic fleet, or rejected machines scatter into unrelated rooms. Changing the provisioning token does not revoke already-running old daemons or open channels; rotation must stop old admission and close/rekey existing access.

8. **Other premise/provisioning corrections.** The host lock is local to one home (`ts/serve.ts:1851`), not a distributed exclusion mechanism across machines. Minted secrets can be generated centrally before imaging (`ts/share.ts:176` shows ordinary random generation), so “fundamentally un-provisionable” is wrong. It is topology that blocks copying today's room to N hosts, not random-secret generation. The current `AY_JOIN` installer executes a foreground daemon (`lab/ui/setup.sh:157`), so copying that shape is not a complete persistent cloud-init/service installation story. Specify service persistence, reboot recovery, secret storage, and migration from an already-installed local daemon. The sample environment assignment applies to the child shell, not automatically to whatever service manager later launches a daemon.

9. **A is the right next step, but “already implements all of it” overstates equivalence.** Agent enumeration/proxying are real (`codehost/src/cli/plugins/agent-yes.ts:67`, `:129`) and agent-yes already consumes them. The plugin advertises at most 50 agents (`:18`), requires a running HTTP `ay serve` for control (`:141`, `:148`), and defaults to port 7432 (`:16`); `--webrtc`-only is insufficient. Existing RTC is STUN-only (`codehost/src/shared/rtc.ts:3`), unlike agent-yes's host-supplied TURN (`ts/share.ts:108`). The codehost Worker receives the bearer secret in its URL, and its RTC-to-tunnel path opens directly on the channel (`src/web/room-client.ts:103`), without agent-yes's secret-derived transcript key confirmation. Do not describe A as maintaining protection from a compromised signaling server.

   There is also a concrete codehost roster hazard: `worker/room.ts:179` documents the attachment size limit, but its trimming loop only reduces workspaces (`:195`). A large agent advertisement can fail attachment serialization and still receive `welcome` (`:87`); “proven” does not make this safe for large fleets.

   Acceptance work should be: provision two hosts with one centrally generated token using A; see and control both in agent-yes's existing console; include duplicate hostnames/PIDs, an empty host, restart, HTTP daemon down, and a network needing relay. Determine whether codehost's signaling trust and connectivity limitations are acceptable. Only a demonstrated requirement to preserve agent-yes's stronger signaling threat model, TURN behavior, or independent operation justifies C. The room-layer argument does not.

No product source was changed. This review artifact is the only file added; no rebuild/relink was needed.
